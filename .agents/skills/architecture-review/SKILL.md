# アーキテクチャレビュースキル

技術提案・システム設計・インフラ選定をITアーキテクトの観点から分析する。

## 実行手順

### Step 1: 非機能要件の確認

```markdown
## 非機能要件チェック

| 観点 | 要件 | 現在の設計での対応 | ギャップ |
|---|---|---|---|
| 可用性（SLA） | {X}%（月X時間停止まで許容） | {対応状況} | {ギャップ} |
| パフォーマンス | レスポンス{X}秒以内、同時接続{X}件 | | |
| スケーラビリティ | {X}年後のX倍トラフィック | | |
| セキュリティ | {認証・認可・暗号化方針} | | |
| 障害復旧（RTO/RPO） | RTO: {X}時間以内、RPO: {X}時間分のデータ | | |
| コンプライアンス | {GDPR・個人情報保護法等} | | |

**未定義の非機能要件**: {要確認事項}
```

### Step 2: アーキテクチャ評価

```markdown
## アーキテクチャ評価

### 構成概要（現状/提案）
```
[クライアント] → [ロードバランサー] → [アプリサーバー] → [DB]
                                    ↓
                              [キャッシュ層]
```

### 強み
- {良い設計判断とその理由}

### リスク・懸念点
| リスク | 深刻度 | 改善案 |
|---|---|---|
| 単一障害点（SPOF）: {箇所} | 高/中/低 | {対策} |
| スケーラビリティボトルネック: {箇所} | | |
| 技術的負債: {箇所} | | |
```

### Step 3: セキュリティレビュー（OWASP Top 10）

```markdown
## セキュリティチェック（OWASP Top 10）

| # | 脅威 | リスク評価 | 現在の対策 | 追加対策の推奨 |
|---|---|---|---|---|
| A01 | アクセス制御の不備 | 高/中/低/N/A | {対策} | {推奨} |
| A02 | 暗号化の失敗 | | | |
| A03 | インジェクション | | | |
| A04 | 安全でない設計 | | | |
| A05 | セキュリティ設定ミス | | | |
| A06 | 古いコンポーネント | | | |
| A07 | 認証・認可の失敗 | | | |
| A08 | データ整合性の失敗 | | | |
| A09 | ログ不足 | | | |
| A10 | SSRF | | | |

**要対処の最重要項目**: {Top 3}
```

### Step 4: 技術選定評価

```markdown
## 技術選定レビュー

### 採用技術の評価
| 技術 | 採用理由 | 懸念点 | 代替案 | 推奨 |
|---|---|---|---|---|
| {技術名} | {理由} | {懸念} | {代替} | ◎/○/△/✗ |

### 技術的負債評価
| 負債項目 | 現在の影響 | 将来の影響 | 返済コスト推定 |
|---|---|---|---|
| {項目} | {影響} | {将来リスク} | {工数} |
```

### Step 5: アーキテクチャ上の推奨事項

```markdown
## アーキテクチャ観点の結論

**総合評価**: {採用推奨 / 条件付き推奨 / 要再設計}

**必須対応事項（Goに向けた条件）**:
1. {最重要の修正事項}
2. {次点}

**推奨改善事項（中期）**:
- {将来に向けた改善}

**考慮不要な事項（Over-engineering 防止）**:
- {現時点では不要な複雑化の提案}
```

## 注意事項

- OWASPセキュリティチェックは必ず実施する（省略不可）
- 「シンプルで十分」な場面でマイクロサービス等を推奨しない
- コスト概算は経理専門家と連携する
- 具体的な実装コードの提供はai-secretary（github-review等）に委ねる
