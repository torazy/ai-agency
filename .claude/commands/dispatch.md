# /dispatch ── 割り振り役・確認役（定期の見直し）

ユーザー入力：`/dispatch`（無人は `/dispatch --unattended`。`--dry-run` で判断だけして起動しない。`--no-observe` で観察を省く）

入力（引数）: $ARGUMENTS

@chief が**割り振り役**（提案をさばいて仕事を振る）と**確認役**（成果を受け入れるか決める）を順に務める。
提案役（/scout）が見つけた仕事を**そのまま全部は実行しない**。役ごとに責任を分け、判定には必ず理由を残す。

## 守ること

- 本体（`.ai-agency-template`）では何もしない
- 上限はプログラムが強制する（`work/settings.md`：同時実行の上限・1日の費用上限・1回の上限）。超えたら起動しないで次回へ
- **自動で着手してよいのは**、`work/settings.md` の「自動で着手」が `委任範囲` で、かつ `memory/delegation.md` の
  「チームの自動運転で任せてよい仕事」に当たるものだけ。それ以外は判定を**要承認**にして人に回す（推奨の担当・期限・理由を添える）
- 無人では：質問しない。約束を完了にしない（受け入れまで。完了は人）。記憶（人物・案件・決定）を書き換えない。外部へ送信しない
- 同じ変化を二度処理しない：変化は提案の起因（指紋）で1回だけ提案され、処理したら `work.py ref touch` で版を進める

## 1. 状況を確かめる（トークンを使わない）

```bash
python tools/work.py status --json        # 上限・今日の費用・実行中・未確認の実行・変化・未判定の提案
python tools/work.py changes --propose    # 関連情報の変化 → 提案（重複しない）
python tools/work.py scan --propose       # フォロー日・期限が近いのに未着手 → 提案
```

続けて `/scout` の 2〜3 で観察による提案を足す（無人でも行う。多くても7件）。`--no-observe` のときは省く（定期実行は観察の間隔が来た回だけ観察する。仕事も観察も無い回は、tools/schedule/dispatch.py が `work.py pending` で確かめて Claude を起動しない）。

## 2. 確認役：終わった実行を確かめる（未確認の実行ごと）

報告 `memory/work/results/{実行ID}.md` と作業依頼（`work.py show`）を読み、次を照らす：

1. 完了条件を1つずつ満たしているか（報告の「完了条件の確認」を鵜呑みにせず本文で確かめる）
2. 主張に根拠と出所があるか。レビューがあれば判定と残った指摘
3. 使った版が今も有効か（`work.py accept … accept` が前提の参照・作業依頼・報告のあとの途中の変更を検査し、古ければ「古い条件」にする）

判定（`python tools/work.py accept C-007-R2 accept|return|ask --reason "…"`）：

| 判定 | とき | 次 |
|---|---|---|
| 受け入れ | 条件を満たし、根拠があり、古くない | 人の承認待ち（ボードの「承認して完了」）。完了にはしない |
| 差し戻し | 直せば満たせる不足がはっきりしている（2回まで） | `work.py note` に不足を書き、委任範囲なら作業セッションを再起動 |
| 人へ確認 | 人の判断が要る・差し戻しが2回に達した・方針が割れた | 要点と問いを dispatch.md と報告の先頭に。人の回答は `work.py note`：成果物を変える回答はそのまま（報告は古い条件になり、やり直す）、「このままで可」など変えない回答は `--info` |
| 古い条件 | 実行中・実行後に前提が変わった | 下の 4 の「見直し」と同じ扱い（新しい条件でやり直すか判断） |

確認役は自分で成果物を直さない。直しは作業役（作業セッション）に戻す。

## 3. 割り振り役：提案を選別する（未判定の提案ごと）

判断の観点：**必要性**（目的・期限に効くか）／**重複**（既存の約束・作業記録と同じなら統合）／**優先度**（期限・影響・待っている人）／
**依存関係**（前工程が終わっているか。終わっていなければ後工程の参照に入れて保留）／**委任範囲**／**作業量と稼働**（実行中の数・今日の費用）。

```bash
python tools/work.py decide S-004 merge --task C-007 --reason "C-007 の比較表更新と同じ。途中の変更として渡す"
python tools/work.py decide S-005 hold --reason "前工程 C-006 が未完了。C-006 の後工程として参照に登録"
python tools/work.py decide S-006 reject --reason "既に 11/10 の定例で扱う（C-002）"
python tools/work.py decide S-007 ask --reason "部長への催促は人の判断。推奨：@chief が下書き、期限 11/7"
```

**採用する**とき（委任範囲のみ。それ以外は ask）：

1. 採用して約束台帳に載せる：`python tools/work.py adopt S-008 --who @pm --content "…" --due … --rel P:… --reason "…"`（出力の C-ID を使う。採用済みの提案なら新しく作らずに既存の C-ID を返すので、やり直しても仕事が2件にならない）
2. 作業依頼を書く：`python tools/work.py order C-012 --purpose … --deliverable … --done-when … --ops "読み取り・Web 調査・報告の作成"
   --limit "2.5 USD" --review "qa（部長に出すため）" --escalate "…"`（進め方は independent-review の 1 で決める）
3. 参照を登録する：その仕事が依存する情報（`ref add C-012 "memory/…#節" --use 前提|待ち`、前工程は `C-006 --use 後工程`）。
   **ここを書くことで、本文が変わらなくても関連情報の変化で再評価される**
4. 着手できるなら起動：`python tools/run_task.py C-012`（上限に当たれば次回）

## 4. 変化に由来する提案の扱い

| 種類 | 割り振り役の判断 |
|---|---|
| 再開（待ちが解消） | 待っていたものが本当に届いたかを確かめ、`work.py note` に届いた内容の座標を書き、`work.py decide S-… merge --task C-… --reason "…"` で届いたことにしてから起動（判定する前は着手条件がそろわず起動できない）。届いていなければ `ref touch` して却下。人に確かめるなら hold（あとで決め直せる） |
| 着手（前工程が完了） | 前工程の成果（報告）の座標を `note` に書いて起動 |
| 見直し（前提が変化） | **まず影響を判断する**（毎回作り直さない）。結論・成果物・進め方に影響しない → `ref touch` して却下（理由に「影響なし：…」）。影響する → `note` に変化と影響を書き、やり直し（起動）か要承認 |
| 実行中に変化 | 次の4つから選ぶ：①継続（影響が小さい）②軌道修正（`work.py note` に変化を書く。作業セッションは報告前に読む）③止めてやり直す（`python tools/run_task.py --stop C-007 --reason "…"` → 起動）④今の成果を受け取ってから追加作業（終わった後の差し戻しか新しい提案） |
| 完了済みの見直し | 結論が変わり得るかを判断。変わり得るなら要承認（「C-007 の根拠 X が訂正された。見直しタスクを作るか」）。変わらないなら `ref touch` して却下 |

どれも、処理したら `python tools/work.py ref touch C-007 "場所"` で版を進める（同じ変化で二度動かない）。

## 4b. 起動待ち（status の launch_waiting）

作業依頼まで書いたのに一度も起動していないタスクと、差し戻し・古い条件のあと次の実行が無いタスク。上限で断られた、採用と起動を分けた、落ちて「終了不明」になった等で、次の回に拾わないと止まったままになる。
委任範囲なら `python tools/run_task.py C-012` で起動する（上限に当たればそのまま。次の回も起動待ちとして残る）。今は起動しないと決めたら `python tools/work.py defer C-012 "何を待つか"`（人の判断待ち・委任範囲の外など。新しい途中の変更が入れば起動待ちに戻る）。

実行中のまま残っているもの：実行のプロセスが無くなった実行は、起動・状態の確認のときに自動で「終了不明」として閉じられ、未確認の実行として確認役に回る（報告があれば確かめ、無ければやり直す）。実行の記録（.state）が無く確かめられないものは自動では閉じない。人に伝え、止めるなら `python tools/run_task.py --stop C-012-R1`（実行ID で個別に閉じる）。

## 5. 記録して終える

`memory/briefs/dispatch.md` を上書きする（YYYY-MM-DD HH:MM、確認した実行と判定、提案の判定、起動した実行ID、人に相談すること、
上限で見送ったもの）。対話なら要点を伝え、要承認があれば1つずつ問う。無人なら標準出力に1行（「起動 n・確認 m・要承認 k」）だけ。

## 定期実行

`tools/schedule/dispatch.ps1|.sh` をスケジューラに15分ごとで登録する。`work.py tick` が `work/settings.md` の実行間隔で間引く。
間隔・同時実行の上限・1日の費用上限・自動で着手するかは `work/settings.md` で変える（秘書に「1時間ごと・同時に3件まで」と頼んでもよい）。
