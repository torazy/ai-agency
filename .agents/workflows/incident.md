# /incident ── 障害対応ワークフロー

ユーザー入力：`/incident {分かっている状況}`（または障害の報告を検知したら @chief が起動を提案）

あなたは @chief として、**通常タスクをすべて後回しにして**以下を順に実行する。
平時の丁寧な確認より**スピードと記録**を優先するが、外部への送信・実行の承認原則（AGENTS.md §9）は
障害時も変わらない（下書きまで用意して承認を仰ぐ）。

## Step 1: 宣言とログ開始（最初の1分）

1. インシデントログを即作成する：`memory/projects/{name}/incidents/YYYY-MM-DD-{slug}.md`
   （プロジェクト不明なら `memory/memos/` に置き、判明後に移動）
2. 以下のヘッダで開始し、**以後すべての事実・アクションを時刻付きで追記**していく：

```markdown
# インシデント: {タイトル}
- **検知**: YYYY-MM-DD HH:MM（検知経路: Slack/監視/顧客連絡…）
- **状態**: 🔴 対応中 / 🟡 監視中 / 🟢 復旧済
- **影響**: （誰に・何が・どの範囲で。不明なら「調査中」）
- **重大度**: High（顧客影響あり）/ Mid（業務影響）/ Low（内部のみ）

## 時系列ログ
| 時刻 | 事実・アクション | 情報源 |
|---|---|---|
```

## Step 2: 状況収集（座標から直接・並列）

サービス座標を使い、関連情報を集めて時系列ログに追記する：
- **Backlog**: 既存の障害チケット・関連チケット（backlog-search）
- **GitHub**: 直近のマージ・デプロイ・CI状態（github-review）── 「直前に何が変わったか」
- **Slack**: 関連チャンネルの報告状況（slack-via-bot）
- 過去の類似障害：当該プロジェクトの `incidents/` と `insights.md` を検索

## Step 3: 初動の整理と提示

```
## 🔴 インシデント初動サマリー
**何が起きているか**（事実のみ）:
**影響範囲**（確定/推定を区別）:
**直前の変更**（容疑箇所）:
**今すぐやるべきこと（優先順）**:
1. {暫定対処（止血）}
2. {連絡すべき相手と内容}
3. {原因調査の次の一手}
```

## Step 4: 連絡の下書き（送信はしない）

関係者への第一報・続報の下書きを用意する（宛先ごとにトーンを変える）：
- 上司向け：結論先行・影響・対応状況・次報予定時刻（人物モデルが Lv2 以上なら様式を合わせる）
- チーム向け：事実・役割分担・作業依頼
- 顧客向け（必要時）：@legal の観点確認を推奨
「▶ 送信してよいですか？」で承認を取ってから送る。

## Step 5: 復旧確認とクローズ

- 復旧の確認方法を明示し、確認できたらログの状態を 🟢 に更新
- 暫定対処で終わっている場合は恒久対策を `issues.md` に起票提案
- 対応中に発生した約束（「明日続報を報告する」「xxシステムの機能を調査する」等）は
  `commitments.md` に記録し、関連欄に `P:{名}/incidents/{当該ログ名}` を必ず入れる
  （後で synthesize-situation がこの障害に紐づくタスクを一覧できる）

## Step 6: 事後振り返り（クローズ後、日を改めてでもよい）

インシデントログに追記：
```markdown
## 振り返り
- **根本原因**:
- **検知は早かったか**（もっと早く知る方法）:
- **対応で効いたこと / 遅らせたこと**:
- **再発防止**（→ issues.md / Backlog 起票）:
```
学びの一般化は `memory/insights.md` へ。関係者の動き方の観察は `person-model-update` で人物ファイルへ。
