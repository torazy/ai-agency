# 記憶の点検と手直し（memory-review）

情報は貯まるほど古くなり、食い違い、散らかる。**機械的に見つけられるものは `tools/recall.py review` が
トークンを使わずに拾う**ので、秘書は結果を読んで直すことに集中する。量の整理（アーカイブ）は `memory-maintenance`。

## Step 1: 点検結果を得る

```bash
python tools/recall.py review --out memory/briefs/review.md
```
（今日の `/morning-brief` が既に作っていればそれを読む。結果は「秘書が直してよい」と「ユーザーに確認」の2群）

| 区分 | 何を見ているか |
|---|---|
| 食い違い | 台帳の期限と、situation.md・status.md に書かれた日付のずれ（期限の正典は台帳） |
| 古さ | 30日更新のない進行中案件の状況、14日更新のない situation、120日記録のない「重要な人物」、180日前の背景資料 |
| 重複 | 同じメール・同じ氏名の人物ファイル、同じ題の決定 |
| 参照 | 存在しない案件を指す関連欄、人物に解決できない依頼者・相手、存在しないファイルへの参照 |
| 取り出し漏れ | どこからも参照されない14日超の生メモ、アクション・決定が書かれたまま台帳や decisions に紐づかない会議メモ、2日超の inbox 未分類 |
| 期限切れ | 30日超の未承認の提案、期限から14日超の未完了の約束 |
| 育成・量 | 判断事例5件以上で Lv1 の人物、200行超のファイル、完了30行超の台帳、90日前の成果物 |
| 知識 | 確認日から180日たった有効な業務ルール（今も有効か）、同じ言葉が複数の用語に当たる、用語の範囲が存在しない案件 |

## Step 2: 秘書が直す（「秘書が直してよい」群）

直す前に、該当箇所だけを読む（`python tools/recall.py show {path} --section {見出し}`）。表は mem.py 経由。

| 区分 | 直し方 |
|---|---|
| 食い違い | 台帳を正として situation / status の記述を直す。台帳のほうが古い証拠（新しい日付のメール等）があれば `mem.py commitment set-due` |
| 参照（切れた） | 正しいパス・案件に直す。直せないものは参照を外し、事後報告に書く |
| 取り出し漏れ | 会議メモ・生メモの中の約束は `mem.py commitment add`、決定は `mem.py decision add --status proposed`、人物の判断は `mem.py person observe`。取り出したら元のメモに「→ 記録先: …」を1行足す（次の点検で再検出されない） |
| inbox | 仕分けて配置し `inbox resolve`（CLAUDE.md §5） |
| 育成 | 人物ファイルの成熟度を上げる（判断事例の件数を添える） |
| 量 | `memory-maintenance` の手順でアーカイブ |

## Step 3: まとめて1問（「ユーザーに確認」群）

判断が要るもの（案件を完了扱いにするか、人物を重要な人物から外すか、重複が同一人物か、提案を承認するか、
期限切れの約束を done / dropped / 期限延長のどれにするか、解決できない名前は誰か）は、**記録先や選択肢の案を添えて
1メッセージにまとめて**聞く。答えを受けたらその場で反映する。

件数が多いとき（目安10件超）は1件ずつ聞かない。案件ごとにまとめた表に**秘書の推奨**（例：期限切れの約束は
状態が waiting なら「フォロー日を引き直す」、半年動きのない約束は「dropped」）を添え、「推奨どおりでよいか、違うものだけ番号で」と
1問にする。ユーザーは例外だけ答えればよい。点検の出力は区分ごとに上位5件なので、全件は
`python tools/recall.py review --area {区分}` で引いてから表にする。

## Step 4: 事後報告

```
## 記憶の点検（{日付}）
- 🔧 直したもの: {n} 件（例: situation.md の比較表期限 11/14 → 11/13〔台帳 C-003 に合わせた〕）
- ❓ 確認: {上の1問}
- 次の点検: 次回の /morning-brief（点検は毎朝、トークンを使わずに走る）
```
直したあと `python tools/recall.py review` をもう一度走らせ、直した項目が消えたことを確かめる。

## 規律

- 点検の結果は「候補」。直す前に該当箇所を読み、文脈で誤検知なら直さない（例：意図して古い日付を残している履歴の行）
- 削除はしない。誤りは直す、不要は archive か `dropped`
- 人物の判断事例ログは消さない・まとめない（/simulate の素材）
