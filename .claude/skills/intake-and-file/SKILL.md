# インテーク＆ファイリング

外部情報をAI秘書の知識ベースに取り込み、適切な場所に構造化して保存するプロセス。

## 実行手順

### Step 1: 情報の種類を判定する

持ち込まれたテキストを解析し、以下の種類を特定する：

- **会議メモ・議事録** → `meetings/YYYY-MM-DD.md`
- **決定事項・合意** → `decisions.md`（既存ファイルに追記）
- **未解決の問題・課題・懸念** → `issues.md`（既存ファイルに追記）
- **プロジェクト背景・前提・仕様** → `context/{topic}.md`
- **関係者情報** → `memory/people/{name}.md`
- **実在人物の発言・判断・反応**（会議での判断、Slackでの差し戻し等） → 同ファイルの
  ペルソナモデル（判断事例ログ）へ。`person-model-update` スキルを併用する
- **タスク・指示・依頼**（自分のTODO、上司からの指示、部下への依頼、会議のアクションアイテム）
  → `memory/commitments.md`。`commitment-track` スキルを併用する（Backlogチケット級なら起票提案）
- **現状アップデート・進捗** → `status.md`（既存ファイルに上書き）
- **サービス座標** → `overview.md`（サービス座標セクションに追記）
- **「覚えておいて」で分類が即決できないもの** → まず `python tools/mem.py inbox add "要点" --source {出所}`
  （取りこぼしゼロ）。分類後に `inbox resolve` で記録先を残す
- **生メモ・複数カテゴリ混在（長文）** → `memos/YYYY-MM-DD-{topic}.md`
- **ドメイン知識・汎用情報** → `memory/insights.md`

複数の種類が混在する場合は分割して複数ファイルに保存する。

### Step 2: 対象プロジェクトを特定する

1. ユーザーの指示やテキスト内容からプロジェクト名を特定する
2. `memory/dashboard.md` のプロジェクト一覧を参照する
3. 不明な場合はユーザーに確認する

プロジェクト名が特定できた場合：
- 保存先は `memory/projects/{project-name}/`
- `memory/projects/{project-name}/overview.md` が存在しなければ新規作成を提案する

### Step 3: 既存ファイルを確認し、迷ったら確認してから書く

重複・矛盾を避けるため、書き込み前に対象ファイルを読む。

**確信の二段階**：
- 確信あり → 記録して、事後に1行報告（📁 形式）
- 迷い → 書く前に「→ {記録先}として記録します。よいですか？」と**1行で**提示して確認する

**必ず事前確認するもの**（誤記録の影響が大きい）：
1. 新しい人物ファイルを作るとき（同一人物の既存ファイルが無いか、識別子は何か）
2. 案件が複数登録されていて、本文に案件名が無いとき（どの案件か）
3. 「決定」か「案・検討中」か本文から判別できないとき（decisions.md は `提案（未承認）` と `決定` を区別する）
4. 発言・判断の主体（誰が言ったか）が特定できないとき（人物モデルの素材は帰属が命）

確認待ちの間も情報は失わない：先に `mem.py inbox add` で inbox に入れておく。

- ファイルが存在する場合：既存の内容と照らし合わせて追記・更新
- 既存の内容と矛盾する場合：ユーザーに確認してから上書き
- ファイルが存在しない場合：新規作成（`memory/delegation.md` の許可範囲を確認）

### Step 4: 構造化して書き込む

各ファイルタイプの書式に従って内容を整形する。

**会議メモ (`meetings/YYYY-MM-DD.md`):**
```markdown
# YYYY-MM-DD 会議メモ：{会議名}

**日時**: YYYY-MM-DD HH:MM
**参加者**: 氏名1、氏名2
**目的**: 

## 議事内容
（箇条書きで時系列に）

## 決定事項
- 

## アクションアイテム
| 担当 | 内容 | 期限 |
|---|---|---|

## 積み残し・次回議題
- 
```

**決定事項 (`decisions.md`)** ── `python tools/mem.py decision add --project {slug} --title … --content … --reason …
--prediction … --verify-date … [--status proposed|decided]` で追記する（既定は `提案（未承認）`。ユーザーが承認したら
`decision set-status {slug} "{title}" decided`）。生成される書式：
```markdown
## YYYY-MM-DD: {決定の要約}
- **状態**: 提案（未承認）/ 決定 / 検証済
- **決定内容**: 
- **決定理由**: 
- **影響範囲**: 
- **予測（期待した結果）**: {この決定で何が起きると見込むか ── 後で /review-decisions が検証する}
- **検証日**: YYYY-MM-DD {結果を確認する目安日}
- **撤回条件**: （あれば）
- **検証結果**: （/review-decisions が後日追記：予測通り/部分的/外れ ＋ 学び）
```

**現状 (`status.md`)**：進捗・次のマイルストーン・ブロッカーを書く。**期限付きのタスク・指示は書かない**
（それは `commitments.md` に一元記録し、status.md からは「約束は台帳の `P:{slug}` を参照」と書く。同じ事実を
3か所に書かない）。

**課題 (`issues.md`):**
```markdown
## [{severity}] {課題タイトル}
- **発見日**: YYYY-MM-DD
- **状態**: open / in-progress / resolved
- **内容**: 
- **影響**: 
- **対策**: 
```

**人物ファイル (`memory/people/{識別子}.md`):**

人物を一意に特定するためのルール：
- ファイル名は `{姓}-{名}-{所属略称}-{役職略称}.md` の形式にする
  - 例: `tanaka-kenji-abc-corp-cfo.md`
- 同姓同名・組織異動があっても混同しないよう、**メールアドレス・Backlogユーザー名・GitHubアカウント等の一意の識別子を必ず記録する**
- 氏名だけで記録しない（例: `suzuki.md` は禁止）

```markdown
## 基本情報（個人特定）
- **氏名**: 
- **役職・所属**: （現在の組織・部署）
- **メールアドレス**: 
- **Backlogユーザー名**: 
- **GitHubアカウント**: 
- **関係の種別**: 社内同僚 / 顧客 / ベンダー / パートナー

## 業務上の役割
- **担当領域**: 
- **意思決定権限**: 

## 思考・行動特性
- **意思決定スタイル**: 
- **コミュニケーションスタイル**: 
- **優先価値観**: 
- **効果的なアプローチ**: 
- **地雷・避けるべき点**: 

## 過去のやりとり・気づき
| 日付 | 状況 | 気づいたこと |
|---|---|---|
```

詳細は `memory/people/_template.md` を参照。表（判断事例ログ・過去のやりとり・反応予測）への追記は
`python tools/mem.py person observe|note|predict {識別子} …` で行う（`person-model-update` スキル）。

**プロジェクト概要 (`overview.md`):**
```markdown
# {プロジェクト名}

## 概要
- **目的**: 
- **状態**: 
- **開始日**: 
- **期限**: 

## サービス座標
| サービス | 場所 | URL/ID |
|---|---|---|
| Backlog | プロジェクト | {PROJECT_KEY} |
| GitHub | リポジトリ | {owner/repo} |
| Drive | フォルダ | {URL} |
| Slack | チャンネル | #{channel-name} |

## 関係者
| 名前 | 役割 |
|---|---|

## 重要な決定事項
（decisions.md へのサマリーリンク）

## 現在の状態
（status.md へのサマリーリンク）
```

### Step 5: 完了報告と次のアクション提案

ファイリング完了後、以下を報告する：

```
## ファイリング完了

- 📁 {ファイルパス} ── {何をしたか（新規作成 / 追記 / 更新）}
- 📁 {ファイルパス} ── {何をしたか}

**気づいたこと**:
（例：「プロジェクトAのDriveフォルダURLがまだ未登録です。教えていただければ追加します」）

**次のアクション候補**:
（例：「Backlogに課題チケットを起票しますか？」）
```

## 重要な注意事項

- ユーザーが貼り付けたテキストを**そのままコピーしない**。要点を抽出して構造化する
- 固有名詞・数字・日付は原文のまま維持する
- 判断が必要な内容（例：「この決定は正しいか？」）はファイリングと分離して別途回答する
- 個人情報・機密情報は変換せず原文通り記録する（セキュリティはユーザーの責任範囲）
