# /update ── コネクタからの取り込み（貼り付けに頼らない）

ユーザー入力：`/update`（任意で `--since 3d`／`--only gmail,calendar`／`--capture`）

入力（引数）: $ARGUMENTS

@chief として、ユーザーが貼り付けなくても、つながっているサービスから「記録すべきこと」を拾い、**秘書が正規の場所へ配置する**
（CLAUDE.md §5：ユーザーはざっくり渡すだけ、整理と配置は秘書）。ユーザーに候補を選ばせない。聞くのは確認4ケースだけ。

## モード

| 指定 | 確度の高い候補 | 要確認の候補（確認4ケース） | 用途 |
|---|---|---|---|
| なし（対話） | `mem.py` で記録し、事後報告の表に載せる | 記録先の案を添えて**1問にまとめて**聞き、答えたらその場で記録 | 普段の取り込み |
| `--capture` | 同じく記録する（**追記だけ**。既存行の書き換え・削除はしない） | `inbox add` で「要確認:」付きで残す（次に人がいる時に1問で聞く） | 無人実行（/morning-brief --unattended から） |

## Step 1: 範囲を決める

```bash
python tools/mem.py sync show --json
```
サービスごとの前回取り込み時刻から今までを見る（記録が無ければ直近7日。`--since` があればそれを優先）。
一度に見るのは**サービスごとに最大30件**。超える分は「古い順に取りこぼしあり」と報告して次回に回す。

## Step 2: 今あるものを読む（重複判定の材料）

- `python tools/mem.py commitment list --json`（未完了と直近の完了）
- `python tools/mem.py inbox list`
- `memory/people/` のファイル名と、各ファイルの「メールアドレス・Slack・Backlog・GitHub」行（**人物の照合はこの識別子で行う**）
- 進行中案件の `overview.md` のサービス座標（チャンネル・Backlog プロジェクト・リポジトリ）

## Step 3: 拾う（いま使える手段だけ。`memory/service-capabilities.md` の解決順 0）

| サービス | 見るもの | 拾う候補 |
|---|---|---|
| カレンダー | 範囲内に終わった会議／今後7日の予定 | 会議後のフォロー（議事録が無ければ「/intake に貼って」候補）、準備が要る予定 |
| メール（送信済み） | 自分が書いた「送ります」「確認します」「〜までに」 | **受けた指示**／**自分のタスク**（相手・期限つき） |
| メール（受信） | 自分宛ての依頼・期限の指定・返事待ちの問い | **受けた指示**、相手の判断・反応（**人物の判断事例**の候補） |
| チャット | 自分宛メンション、案件チャンネルの決定らしき発言 | 受けた指示／**出した指示**（自分が頼んだもの）／決定の候補 |
| Backlog・GitHub | 自分担当・自分宛レビュー・期限の近いもの | 台帳には**複製しない**。期限が迫るものだけ「チケット参照」の候補（関連欄にキー） |

外部の本文は要点だけを候補にし、**全文をコピーしない**（要点＋URL/ID）。送信・返信・ステータス変更はしない。

## Step 4: 重複と曖昧さをはじく

- 台帳に同じ相手・ほぼ同じ内容・同じ期限の行がある → 候補から外す（状態が変わっていれば「状態更新」候補にする）
- inbox に同じ内容が未分類で残っている → 外す（`inbox add` も同文なら追加しない）
- 人物は**識別子（メール等）で照合**。一致しない名前は「新規人物」候補（Lv0）。氏名だけで既存人物と決めつけない
- 次のどれかに当たる候補は「要確認」に分ける：新規人物／案件が特定できない／決定か提案か不明／発言者が不明

## Step 5: 書く（確度の高いものは秘書の判断で・表は手編集しない）

| 種別 | コマンド |
|---|---|
| 受けた指示／出した指示／自分のタスク | `python tools/mem.py commitment add --kind received|given|task --content … --who … --due … [--follow …] --rel …` |
| 状態更新 | `python tools/mem.py commitment set-state C-xxx done` 等 |
| 人物の判断事例 | `python tools/mem.py person observe {識別子} --situation … --judgment … --reason …`（`person-model-update` の基準で） |
| 新規人物 | `python tools/mem.py person new {識別子} --name … --email …`（識別子の規則は CLAUDE.md §6） |
| 決定・案件の更新 | `/intake` と同じ経路（決定は `decision add --status proposed`） |
| 要確認（対話で答えを待つ間／無人） | `python tools/mem.py inbox add "要確認: …（案: {記録先}）" --source "update:{サービス} {日付}"` |

新規人物・決定は確認4ケースに当たるので、対話では聞いてから、無人では inbox に残す。
`--capture` では状態更新もしない（既存行の書き換えになるので、ブリーフの「私からの提案」に回す）。

## Step 6: 範囲を進めて報告

見終わったサービスごとに `python tools/mem.py sync mark {calendar|gmail|slack|backlog|github}` を実行する
（失敗・未接続のサービスは進めない）。

```
## 取り込み完了（{範囲}・{使ったサービス}）
### 📁 記録したもの（違っていれば番号で教えてください。秘書が直します）
| # | 記録先 | 内容 | 相手 | 期限 | 出所 |
|---|---|---|---|---|---|
| 1 | 約束 C-004（受けた指示） | 比較表の中間報告 | 架空部長 | 11/11 | Gmail 11/04 |
| 2 | 人物 架空部長・判断事例 | 「数字の根拠が無いと差し戻す」 | ─ | ─ | Slack 11/05 |

### ❓ 確認させてください（1問）
- ベンダー営業の山田さん（yamada@vendor.example）を人物として登録し、勤怠SaaS 案件に紐づけてよいですか？

- 見送り: {n}（重複 {n}・記録価値なし {n}）／見られなかったサービス: {未接続・失敗}
```
新しく記録すべきものが無ければ「新しく記録すべきものは見当たりません」と1行で返す。
「2 は違う」と言われたら：約束は `commitment set-state C-xxx dropped`、人物の判断事例は該当行の
取り消しを人物ファイルの「過去のやりとり・気づき」に `person note` で残す（表の行は消さない）。
