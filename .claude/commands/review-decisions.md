# /review-decisions ── 決定の成果検証（フィードバックループ）

ユーザー入力：`/review-decisions`（または Scheduled Task から週次起動）

入力（引数）: $ARGUMENTS

「予測しっぱなし」を防ぎ、判断精度を上げるためのループ。

## Step 1: 検証対象を集める
以下を走査し、**状態が `決定` で、「検証日」が今日以前で、まだ検証されていないもの**を抽出する
（`提案（未承認）` は検証しない。30日以上放置された提案は別枝で「承認か取り下げか」を1行で聞く）：
- 全プロジェクトの `memory/projects/*/decisions.md`（決定の予測）
- `memory/people/*.md` の「反応予測と検証」テーブル（`/simulate` の人物反応予測）

## Step 2: 各決定について予測vs実際を突き合わせる
```
## 検証: {YYYY-MM-DD の決定タイトル}
- **決定内容**: {何を決めたか}
- **当時の予測**: {期待した結果}
- **実際の結果**: {Backlog/GitHub/会話/ユーザー確認から分かる現状}
- **判定**: 予測通り / 部分的 / 外れた
- **差分の原因**: {なぜズレたか（外れ・部分の場合）}
```
実際の結果がデータで分からない場合は、ユーザーに1問だけ確認する。

## Step 3: 学びを記録する
- `memory/insights.md` に「予測が外れたパターン」「効いた判断軸」を追記する。
- 関係する専門家領域の傾向（例：@accountant の見積りが楽観的になりがち 等）も記録する。
- 当該 decisions.md の項目に「**検証済（{判定}・{日付}）**」を追記する。
- 人物反応予測の場合：該当人物ファイルの検証テーブルに実際の反応・判定・学びを追記し、
  的中実績に応じてモデル成熟度を再評価する（`person-model-update` スキルの基準）。

## Step 4: サマリー出力
```
## 決定レビュー結果（{件数}件）
- ✅ 予測通り: {n}件
- 🟡 部分的: {n}件
- 🔴 外れ: {n}件（→ insights.md に学びを記録）

**今回の最大の学び**: {1つ}
**次に活かすこと**: {具体的な1つ}
```
