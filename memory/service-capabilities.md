# サービス能力マップ

> 秘書がサービスへどうアクセスするかの**規則**と、各ホストで実際に何が使えたかの**観測記録**。
> 「できる/できない」を**この表から思い込まない**。使えるかどうかは、セッションで実際に利用可能な
> ツール（MCP・コネクタ・ブラウザ操作・ホスト固有スキル）を確認して判断し、違っていたら表を更新する。
> 追加・更新は `/setup`（棚卸し）と `capability-expansion` スキルが行う。

---

## 原則

- **実データは各サービスが原本**。ここ（memory/）には座標（URL・ID・キー・チャンネル名）と要点だけを
  記録し、座標から都度取得する。グローバル座標は `memory/dashboard.md`、案件固有の座標（Backlog
  プロジェクトキー・リポジトリ・Driveフォルダ・Slackチャンネル）は各 `memory/projects/{name}/overview.md`。
- **スキルの手順本体は手段非依存**（何を探し・どう整理するか）。手段だけを下の解決順で読み替える。

## 手段の解決順（ツール非依存の共通規則）

どのホストでも、サービスへのアクセスは**この順で解決**する。上位が使えなければ次に落ちる：

0. **いま使えるツールを確認する**（毎回）── セッションのツール一覧に `mcp__{server}__*` があるか、
   ブラウザ操作ツールがあるか、接続失敗と報告されている MCP はないか。
   下の観測記録と違えば観測記録を直す（記録より現物が正）
1. **MCP／公式コネクタ**（最速・最確実）── あればこれ一択。読み取りはそのまま、書き込み・送信は
   `memory/delegation.md` に従い事前提示→承認
2. **ブラウザ操作**（環境が対応する場合のみ）── ログイン済みブラウザで座標の URL を直接開く
3. **手動アシスト**（最後の砦・全環境で可能）── 座標から URL を組み立てて提示し、
   「これを開いて内容を貼り付けてください」と依頼する。取得後の整理・ファイリングは秘書が行う

手段が無くても「できません」で止めず、必ず 3 まで落とす。

## 観測記録（ホスト別・/setup が更新）

> 縦持ち（ホスト×サービスで1行）。同じホスト×サービスの行は上書きする。「手段」は上の番号＋具体名
> （例：`1: MCP github` / `1: コネクタ gmail` / `2: ブラウザ` / `3: 手動` / `✕ 失敗（理由）`）。

|---|---|---|---|
| Dropbox | Level 1 | ブラウザスキル作成で対応可 | 未着手 |
| Confluence | Level 2 | コミュニティMCPあり | 未着手 |

## 対応レベルの定義

- **Level 1**: ブラウザ操作スキルの作成で対応可能。軽い確認で秘書が自律作成。
- **Level 2**: コミュニティMCP／公式コネクタの設定で対応可能。内容を提示して承認を得る。
- **Level 3**: カスタム実装（MCP開発）が必要。要件・工数・選択肢を整理して判断を仰ぐ。
