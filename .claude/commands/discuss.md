# /discuss ── ディスカッション（混成パネル・ラウンド制）

ユーザー入力：`/discuss {テーマ}`（任意で `参加: @accountant @legal 田中部長` と `ラウンド: 2`）

入力（引数）: $ARGUMENTS

あなたは @chief（司会）として振る舞う。`/consult` が「専門家の答えを統合する」のに対し、`/discuss` は
**参加者同士をぶつけて論点を深める**。専門家は「正しい答え」、人物モデルは「実際のあの人の反応（予測）」を
出す別物なので、同じ卓に座らせても**ラベルを分けて混ぜない**。

## Step 1: テーマと問いを固める

```
## ディスカッションの設定
**テーマ**: {1文}
**決めたいこと／深めたいこと**: {問いの形に。例「クラウド型を本命にしてよいか」}
**前提（事実）**: {ユーザーが述べた事実・制約・期限}
**座標**: {memory/projects/{slug}/…、memory/people/…、チケット}
```
問いが曖昧なら1問だけ確認して止まる。

## Step 2: 参加者を決める（3〜5名）

- **専門家**：テーマに関係する観点から `.claude/agents/` の handle を選ぶ（`memory/team/roster.md`）
- **人物モデル**：`memory/people/` の成熟度 **Lv1 以上**だけ指名できる。Lv0 は「観察が無いので参加できません」と伝える
- ユーザーが指名していれば従う。指名が無ければ @chief が案を出す
- **表示名を決める**：専門家は `@handle`、人物モデルは `{呼び名}（予測）`（例：架空部長（予測））。以後の宛先・表・議事録は
  この表示名で統一する。エージェント定義の `icon:`／人物ファイルの `アイコン` が絵文字なら表示名の前に添えてよい

**重い処理なので着手前に1行で確認する**（目安：1名×1ラウンドで約8〜10万トークン・1〜2分。3名×2ラウンドなら
合計 約25〜30万トークン・全体 約8分）：
「参加 {n} 名（専門家 {a}・人物モデル {b}）× {r} ラウンド＝約 {n×r×9} 万トークン・約 {分} 分の見込みで並列召集します。進めますか？」
既定は 2 ラウンド。3 ラウンド目（収束）は対立が残ったときだけ。

## Step 3: ラウンド1 ── 意見表明（並列・独立）

参加者ごとに **Agent ツール**で独立コンテキストを起こす（1メッセージで全員並列）：

- **専門家**：`subagent_type` に handle。人格・共通規則はエージェント定義が持つ
- **人物モデル**：`subagent_type: general-purpose`。指示書は `/simulate` Step 3 の雛形
  （観察記録の抜粋＝思考・行動特性／判断の癖・口癖／判断事例ログ全行／過去の予測の学び）を使い、
  「本人ではなくモデル」「観察に無い領域は創作せず低確度と明記」を冒頭に置く。
  出力形式は下のブリーフと同じ4項目に揃えさせ、「1. 立場」には第一反応の温度感（一言）を、
  「2. 根拠」には判断事例の実例と確度（高＝直接前例あり／中＝特性からの類推／低＝データなし）を添えさせる

全員に**同じブリーフ**を渡す（`/consult` と同じ規律：事実と座標と問いだけ。@chief の仮説・推奨は書かない）：

```
## ディスカッション「{テーマ}」── ラウンド1
## 事実（ユーザーが述べたこと・制約）
{箇条書き}
## 座標（必要なら自分で読む）
{パス}
## 問い
{Step 1 の問い}
## あなたの出力（本文 30 行以内。詳細は「## 付録」へ。付録は 15 行以内）
1. 立場（賛成／条件付き／反対／保留）と、その一言
2. 根拠（数字・規則・前例。人物モデルは「過去にこう判断した」の実例）
3. これが崩れたら立場が変わる前提
4. 他の参加者に聞きたいこと（1〜2問。宛先は役割名で）
```

## Step 4: ラウンド2 ── 反論・修正（同じサブエージェントを継続）

各参加者に **SendMessage（同じ agent を継続）**で、**他の参加者のラウンド1の 1〜4（立場・根拠・前提・問い）を
本文のまま貼る**（付録は貼らない。要約・転記し直しをしない＝司会の手間と改変を減らす。@chief の評価や裁定は書かない。
人物モデルの発言には表示名の「（予測）」が付いていることを確認する）：

```
## ラウンド2：他の参加者の意見を読んで答えてください
{参加者ごとに：役割名／立場／根拠／前提／あなたへの問い}
## あなたの出力（本文 30 行以内）
1. 立場は変わったか（変わった／変わらない）と理由
2. 誰のどの根拠に同意するか、どれに反論するか（根拠付きで）
3. 自分に向けられた問いへの答え
4. 譲れない条件（これだけは満たしてほしい、の1〜2点）
```

分析が逐次依存するとき（A の試算が B の前提になる等）は順番に回す。それ以外は並列。

## Step 5: ラウンド3 ── 収束（対立が残ったときだけ）

ラウンド2で立場が割れたままなら、割れている参加者にだけ送る：
「合意できる条件付きの案はあるか。無ければ最終立場と、相手案を採る場合の最小限の歯止めを1つ」。

## Step 6: @chief の統合

```
## ディスカッション結果：{テーマ}
{1〜3文の結論。人物モデルが関与した部分は「（予測）」を付ける}

### 参加者と最終立場
| 参加者 | 種別 | R1 | R2/R3 | 譲れない条件 |
|---|---|---|---|---|
| @accountant | 専門家 | 条件付き | 条件付き | 5年TCOの上限 |
| 田中部長（モデル） | 人物・予測 | 反対 | 条件付き | 前例の提示 |

### 合意した点
### 対立が残った点（論点／立場／背景）
### @chief の裁定（根拠の強度 → user-profile の優先価値観 → 過去の decisions の順。多数決ではない）
### ラウンドで変わったこと（誰がどの根拠で立場を変えたか＝この議論の収穫）
### 残論点・次に要る情報
**次のアクション**: {具体的に1つ}
```

## Step 7: 記録する（表の手編集はしない）

1. **議事録**：`memory/projects/{slug}/meetings/YYYY-MM-DD-discuss-{topic}.md` に Step 6 の統合と、
   参加者ごとのラウンド別要約（各3行以内）を保存する（案件が無ければ `memory/memos/`）。全文は保存しない
2. **提案**：`python tools/mem.py decision add --project {slug} --title … --prediction … --verify-date … --status proposed`
   （ユーザーが採用したら `decision set-status … decided`）。`--verify-date` は「結果が分かる日」＝
   `python tools/mem.py commitment list --rel P:{slug}` で該当する約束の期限（報告日・提出日）を引く。無ければ 2 週間後
3. **人物モデルの予測**：人物モデルが参加した場合、その最終立場を
   `python tools/mem.py person predict {識別子} --case "{テーマ}" --prediction "{予測した反応}" --verify-date {実際に話す予定日}`
   で記録し、実際の反応が分かったら答え合わせ（`person-model-update`）に乗せる。予定日も約束台帳から引く
4. **学び**：対立のパターン・効いた根拠を `memory/insights.md` に1〜2行

## 安全規則

- 人物モデルの発言はすべて**予測**。本人の発言として扱わない・引用しない・共有しない
- 本人になりすました文面の作成・送信はしない。人物の評価・査定の材料にしない
- 参加者が memory/ に書くことはない。記録は @chief だけが行う
- ユーザーが途中で口を挟みたい議論（長時間・会議形式）は、このコマンドではなく別セッションでの
  agent teams を検討する（現状は未整備。要望があれば提案する）
