# 約束追跡スキル（commitment-track）

タスク・指示・依頼を `memory/commitments.md` に一元記録し、期限切れ・フォロー漏れを防ぐ。

## トリガー条件

> **相手の名前は人物に解決してから書く**：`python tools/recall.py who {名前}`。1件なら依頼者/相手欄はその人の呼び名で書き、
> 0件・2件以上なら CLAUDE.md §5 の確認ケース。既存の人の別の呼び方だったら `mem.py person add-alias` で足す。

- ユーザーが自分のタスクに言及した（「〜しないと」「〜やっておく」）
- 上司・顧客等からの指示・依頼が会話や持ち込みテキストに含まれる（「部長に〜と言われた」）
- ユーザーが誰かに指示・依頼を出した（「〇〇さんに頼んだ」「チームに指示した」）
- `/intake` の処理中にアクションアイテムを検知した（会議メモのアクションアイテム表と連動）
- タスク・指示の完了/状態変化が判明した

## 実行手順

### Step 1: 種類を判定して振り分ける

| 種類 | 記録先セクション | 必須項目 |
|---|---|---|
| 自分の細かなタスク | 1. 自分のタスク | 期限（不明なら「なし」と明記） |
| 受けた指示・依頼 | 2. 受けた指示・依頼 | 依頼者・期限 |
| 出した指示・依頼 | 3. 出した指示・依頼 | 相手・**フォロー日（必須。期限の1〜2営業日前を提案）** |

**Backlog チケットが既にある/起票すべき規模なら台帳に書かない**：
チケット参照（`PROJ-123`）を関連欄に書くか、起票を提案する。台帳は「チケット未満」の粒度専用。

### Step 2: 案件・課題・障害と関連付ける（重要）

指示・タスクの多くはプロジェクトや障害に紐づく。**関連欄を `-`（紐づきなし）にする前に必ず確認する**：

1. 内容にプロジェクト名・課題・障害・チケットへの言及があるか（「あのプロジェクトの」「障害対応の」等）
2. あれば `commitments.md` 冒頭の記法（`P:{名}` / `P:{名}/issues#{課題}` / `P:{名}/incidents/{ログ}` /
   チケットキー）で関連欄に記録する
3. どのプロジェクトか曖昧なら `memory/dashboard.md` のプロジェクト一覧と照合し、不明なら1問だけ確認
4. 課題への紐づきなら、該当 `issues.md` の課題が存在するか確認（なければ課題の起票も提案）

例：「プロジェクトAの課題Xを整理して明日報告して」
→ 受けた指示に追記：内容=課題Xの整理・報告資料化、期限=明日、関連=`P:project-a/issues#課題X`
→ さらに報告相手の人物モデルが Lv2 以上なら「/simulate で報告リハーサルしますか？」を添える

### Step 3: 記録・更新する（CLI 経由・表の手編集はしない）

```bash
python tools/mem.py commitment add --kind task     --content "…" --due YYYY-MM-DD --rel P:{slug}
python tools/mem.py commitment add --kind received --content "…" --who {依頼者} --due YYYY-MM-DD --rel P:{slug}
python tools/mem.py commitment add --kind given    --content "…" --who {相手} --due YYYY-MM-DD --follow YYYY-MM-DD --rel P:{slug}
python tools/mem.py commitment set-state C-012 done        # 状態変更（open / in-progress / waiting / done）
python tools/mem.py commitment list --rel P:{slug}        # 案件視点の抽出（--json も可）
```

- 追記前に `commitment list` で既存行を確認し、同じ約束の重複行を作らない（状態変化なら `set-state`）
- **台帳が唯一の置き場**：同じタスクをプロジェクト側のファイルに複製しない（案件視点の確認は
  関連欄のフィルタで行う）。ただし課題そのものの進展は `issues.md` に書く（役割分担：
  課題の事実は issues.md、「誰がいつまでに何をするか」は台帳）
- 依頼者・相手が `memory/people/` にいる人物なら名前を一致させる（人物モデルの観察材料にもなる）
- 指示の受け方・出し方に人物の反応が伴う場合は `person-model-update` を併用する

### Step 4: 完了処理

- 状態を `done` に更新（行は消さない ── 月次で memory-maintenance がアーカイブする）
- **仕事を止めている不足**（内容の末尾が「（C-0xx の不足）」。一覧は `python tools/work.py needs`）は `set-state` で閉じない
  （断られる）。答えを残して閉じる：`python tools/work.py answer C-031 "答え"`、無しで進めるなら `--without "理由"`。
  届いた返事（メール・Slack・会議メモ）が開いた不足の相手と内容に当たったら、**1問で確かめてから** answer する
  （「C-031（佐藤さんの見積の再送）にこの返事を答えとして記録しますか？」）。無人では answer しない（提案に書く）。
  相手に連絡した（秘書の下書きを人が送った）と分かったら、ボードの「送った」か `python tools/work.py sent C-031`
- **エージェントに任せた約束（相手が `@handle`）は、報告を受け入れてから閉じる**（`/run-task` の「人が承認したあと」・
  ボードの「承認して完了」）。完了にするのは確認役と人で、秘書が自分の判断で閉じると確認役を飛ばすことになる
- 約束の作業とは別のやり方で済んだように見えるとき（会話で作った成果物が近い内容だった等）は、**閉じる前に1問で聞く**。
  「C-017（@pm の段取り案）は今日のメモで済んだことにしますか？」。済んだと言われたら done、違えば残す。
  ユーザー自身が「終わった」と言ったもの・ユーザーのタスクの完了が会話や持ち込みから明らかなものは、従来どおり事後報告でよい
- 完了時に学び・実績があれば `memory/insights.md` や関連プロジェクトへのファイリングを提案

### Step 5: 簡潔に報告する

```
📌 約束台帳を更新：{セクション} に {ID}「{内容}」（期限 {日付}・関連 {P:...}）
```

迷ったときは記録前に1行で確認する（誰の指示か・どの案件か・期限が読めないとき）。

## morning-brief との連携（参照仕様）

`/morning-brief` は毎朝この台帳をスキャンし、以下を警告する：
- 期限が今日〜3日以内、または超過している行
- フォロー日が到来した「出した指示」（→ 催促の下書きを提案）
- `waiting` のまま7日以上経過した行

## 注意事項

- 期限・フォロー日が聞き取れなかったら1問だけ確認する（不明のまま放置しない）
- 上司からの指示は、内容次第で `/simulate` による報告リハーサルを提案できる
- 台帳が30行を超えたら完了項目のアーカイブを提案する
