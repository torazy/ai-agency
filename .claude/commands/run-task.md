# /run-task ── 作業役（独立した作業セッション）

ユーザー入力：`/run-task C-007 --run C-007-R2 --review auto|none|{handle}`（通常は `tools/run_task.py` が無人の新しいセッションで起動する）

入力（引数）: $ARGUMENTS

このセッションは**1つのタスクの1回の実行**のためだけにある。会話の履歴は無い。手がかりは作業記録
`memory/work/tasks/{C-ID}.md`（作業依頼・参照・途中の変更・実行履歴・引き継ぎ）だけ。@chief として担当エージェントに任せ、
**報告を1つ書いて終える**。確認役（/dispatch）と人が報告を見て、受け入れ・差し戻し・人への確認を決める。

## 守ること（無人）

- `.ai-agency-template` がある（本体）か、引数に `C-数字` と `--run C-数字-R数字` が無ければ、何もせず1行で終える
- **質問しない・確認を待たない**。分からないことは報告の「確認してほしいこと」に書いて先へ進む
- 書いてよいのは `memory/work/results/{実行ID}.md` と、`work.py note|handoff` による作業記録への追記だけ。
  約束の状態・記憶（人物・案件・決定・用語）・外部サービスは変えない。記憶に入れるべきことは報告の「記憶に入れる候補」に書く
- `tools/` の命令は `python tools/work.py show C-007` の形のまま1つずつ実行する。`cd`・`&&`・パイプ・リダイレクト（`2>&1` 等）を
  付けると無人では許可されず止まる（承認する人がいない）
- 作業依頼の「実行してよい操作」を超えない。外部への送信・作成・更新はしない（下書きは報告に書く）
- 費用は上限で打ち切られる。直しが回せないときは判定を「要修正 → 未修正」とし、結論の先頭に「このまま出さない」と書く。
  大きすぎるタスクは、できた範囲と残りを報告し、`work.py handoff` に続きの手がかりを残して終える

## 手順

1. **作業依頼を読む**：`python tools/work.py show C-007`（目的・成果物・完了条件・実行してよい操作・期限・上限・レビュー・
   報告先・行き詰まったら／参照と評価した版／途中の変更／前回までの実行と引き継ぎ）。前回の報告があれば
   `memory/work/results/` の直前の実行IDを読み、差し戻しの理由や引き継ぎを**続きとして**扱う（一からやり直さない）
2. **座標を集める**：参照の場所と、目的の固有名詞を `python tools/recall.py decode "…"`／`find`／`who` で引き、
   読むべきファイルの**パスと節**を拾う（中身を丸写ししない）
3. **任せる**：Agent ツールで `subagent_type` に担当の handle を指定して呼ぶ。**description は「{C-ID} {要約}」で始める**。
   ブリーフは作業依頼そのもの（目的・成果物・完了条件・実行してよい操作・期限）＋座標＋途中の変更。@chief の仮説や推奨は書かない。
   返答の形：①結論 ②根拠と出所 ③記憶に入れる候補（記録先の提案つき）④未確認・人の判断が要る点 ⑤使った情報（場所と時点）
4. **報告の下書き**：返答を下の形にまとめる。完了条件を1つずつ照らし、満たしていないものは「確認してほしいこと」に書く
5. **レビュー**（`independent-review` の 2〜3）：`--review` が none なら付けない／handle ならその人／auto なら表で決める。
   重大な指摘があれば作成者を**呼び直して**1回だけ直させる（description「{C-ID} 修正：…」、元のブリーフ＋下書き全文＋重大な指摘）。
   前の呼び出しの続き（SendMessage）が使えなくても止まらない。もう一度レビューには回さない
6. **途中の変更を確かめる**：報告を書く直前に `python tools/work.py show C-007` の「途中の変更」をもう一度見る。
   実行中に足された変更があれば、結論への影響を判断し、影響があれば反映するか（作成者を呼び直す・上限内で）、
   反映できなければ結論の先頭に「途中の変更（…）は未反映」と書く
7. **報告を書く**：`memory/work/results/{実行ID}.md`。途中で終わる・続きがあるなら `python tools/work.py handoff C-007 "…"`
8. 標準出力には1行（「{実行ID}：結論の要点（レビュー：判定）」）だけ返して終える

## 報告の形

```markdown
# {実行ID} {目的}

- 担当: @handle ／ 期限: YYYY-MM-DD ／ 関連: P:slug
- 実行: YYYY-MM-DD HH:MM（無人・独立セッション）
- 使った情報: memory/projects/x/status.md#見積（版 3f2a91c0）・C-006（done）…（作業記録の参照と、追加で読んだもの）

## 結論
（2〜5行。依頼に対する答え）

## 完了条件の確認
- [x] 条件1 …（どこで満たしたか）
- [ ] 条件2 …（満たせなかった理由）

## 根拠と出所
- …（URL・ファイルの座標）

## 記憶に入れる候補
| 記録先 | 内容 | 出所 |
|---|---|---|

## 確認してほしいこと
- …（人の判断が要る点・未確認・依頼とのずれ。無ければ「なし」）

## レビュー
- レビュアー: @qa ／ 判定: OK | 要修正 → 修正済み（1回） | なし（理由）
- 指摘と対応: …
- 残った指摘: …（無ければ「なし」）
```

## 人が承認したあと（対話のとき）

- 起動時の案内に「報告が届いて確認待ち」が出たら、報告を読んで要点を伝え、承認を1問で聞く。承認なら
  `python tools/work.py accept {実行ID} accept` → `commitment set-state … done`（古い条件なら受け入れられない。やり直す）
- 「承認済みで記憶への反映待ち」（ボードで「承認して完了」されたもの）が出たら、報告の「記憶に入れる候補」を通常の手順
  （intake-and-file・commitment-track・person-model-update）で記録する。決定は**提案（未承認）**として入れ、「確認してほしいこと」は
  約束台帳や issues に残す。記録し終えたら `python tools/run_task.py --applied C-…` を実行し、記録先を事後報告する
- 手直しを頼まれたら、`work.py note C-… "…"`（または作業依頼を `work.py order` で直す）→ ボードの「やり直させる」か
  `python tools/run_task.py C-…`。前回の報告と引き継ぎは次の実行が読む
