# 品質レビュースキル

システム・計画・成果物を品質の観点から分析し、テスト戦略と品質リスクを提示する。

## 実行手順

### Step 1: 品質リスク評価

```markdown
## 品質リスク評価

| 機能/領域 | リスク内容 | 影響 | 確率 | 優先度 | テスト重点度 |
|---|---|---|---|---|---|
| {機能} | {リスク} | 高/中/低 | 高/中/低 | {P×I} | ◎最優先/○通常/△軽微 |

**最重要テスト対象**: {優先度の高い機能・シナリオ}
```

### Step 2: テスト観点チェックリスト

```markdown
## テスト観点

### 機能テスト
- [ ] 正常系: {代表的な正常ケース}
- [ ] 異常系: {エラーケース・不正入力}
- [ ] 境界値: {数値の最大・最小・ゼロ・空文字}
- [ ] 権限テスト: {ロール別の動作確認}

### 非機能テスト
- [ ] パフォーマンス: {想定アクセス数でのレスポンス時間}
- [ ] セキュリティ（OWASP Top 10）:
  - [ ] インジェクション（SQL・コマンド）
  - [ ] 認証・セッション管理
  - [ ] XSS（クロスサイトスクリプティング）
  - [ ] 機密データの露出
  - [ ] アクセス制御の不備
- [ ] 可用性・障害復旧: {サービス停止時の動作}
- [ ] データ整合性: {整合性が崩れる操作パターン}

### 回帰テスト
- [ ] 既存機能への影響範囲: {変更の波及が疑われる機能}
```

### Step 3: テスト戦略の提案

```markdown
## テスト戦略

### 自動化すべきテスト
| テスト種別 | 自動化優先度 | ツール候補 | 理由 |
|---|---|---|---|
| 単体テスト | 最高 | {言語に応じたFW} | 繰り返し頻度が高い |
| API テスト | 高 | Postman/pytest-httpx | 変更の影響を早期検知 |
| E2E テスト | 中 | Playwright/Selenium | コスト高・保守に注意 |

### 手動テストが必要なもの
- {UX・ユーザビリティの判断が必要なケース}
- {探索的テスト（想定外の使い方）}

### 完了基準（Exit Criteria）
- バグ未解決件数: 優先度High = 0件、Medium = {X}件以下
- テストカバレッジ: {X}% 以上
- 性能基準: レスポンス {X}秒以内（{Y}%tile）
```

### Step 4: 品質所見サマリー

```markdown
## 品質観点の総評

**品質リスクレベル**: {高 / 中 / 低}

**主な懸念事項**:
1. {最重要懸念}
2. {次点}

**リリース判断の推奨**: {OK / 条件付きOK / 要追加テスト}

**条件（条件付きOKの場合）**:
{この条件が満たされればリリース可}
```

## 注意事項

- セキュリティ観点は省略しない（OWASPチェックは必須）
- 「バグ0で品質が高い」ではなく「重要な欠陥が残っていないこと」が品質
- テスト工数の見積もりは楽観しない（実績工数の1.5〜2倍を見込む）
