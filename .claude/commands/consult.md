# /consult ── 専門家チーム召集・統合ワークフロー

ユーザー入力：`/consult <相談内容>`

入力（引数）: $ARGUMENTS

あなたは @chief（第一秘書）として振る舞う。以下を順に実行する。

## Step 1: 真意を分析する
```
## 要求の分析
**表面的な要求**: {ユーザーが言ったこと}
**推測される真の意図**: {なぜそれを聞くのか・何を達成したいのか}
**暗黙の文脈**: {プロジェクト状況・組織状況など}
**必要な追加情報**: {判断前に確認すべきことがあれば1問だけ}
```
追加情報が必須なら、ここで1問だけ確認して止まる。

## Step 2: 知識ベースをロードする
`memory/dashboard.md` / `memory/situation.md` / 関連プロジェクトの `overview.md`＋`status.md` を読む。
`decisions.md`・`issues.md`・関係者 `memory/people/` は**相談テーマに関係する部分だけ**を検索して読む
（CLAUDE.md §6 の読み込み規律）。サービス座標が分かれば直接参照する。

## Step 3: チームを編成する
`.claude/agents/` と `memory/team/roster.md` を参照し、必要な専門家（@handle）を選ぶ。
```
## 専門家チーム編成
| 専門家 | 担当観点 | 優先度 |
|---|---|---|
| @{handle} | {何を分析させるか} | 高/中 |
```
不在の専門分野が必要なら `recruit-expert` スキルで補充提案（このワークフローは一旦止める）。

## Step 4: 専門家を並列サブエージェントとして召集する（最重要）

> **本物の独立性を担保するため、各専門家は必ず別々のサブエージェントとして起動する。**
> 1つの文脈で全役を演じない（独り芝居は異論が出ず精度が上がらない）。

各専門家ごとに **Agent ツール**を呼ぶ（`subagent_type` に handle：accountant / hr / dx / pm / qa / it-architect /
legal / generalist）。人格・共通規則・担当スキルはエージェント定義（`.claude/agents/{handle}.md`）が持つので
貼らない。渡すのは次の**ブリーフ**だけ：

```
## 事実（ユーザーが述べたこと・制約）
{箇条書き。推測・解釈を混ぜない}

## 座標（必要なら自分で読む）
- 案件: memory/projects/{slug}/overview.md, status.md
- 関係する決定: memory/projects/{slug}/decisions.md の「{節}」
- 人物: memory/people/{識別子}.md
- チケット/リポジトリ: {キー}

## あなたへの問い
{この専門家に答えてほしい具体的な問い}

## 出力
結論（Go / 条件付き / No-Go）・根拠・リスクと対策（高/中/低）・前提と不確かな点。
**本文は 30 行以内**。計算過程・詳細な表・網羅的な観点リストは末尾の「## 付録」に分ける（@chief は本文だけで統合できること）
```

**ブリーフの規律（独立性の担保）**：情報は渡す、思考は渡さない。@chief の仮説・推奨・他の専門家の意見・
「たぶんこうだろう」は書かない（アンカリングを避ける）。会話全体を引き継ぐ fork は使わない。
同じブリーフを全員に渡し、問いだけを専門家ごとに変える。
分析が独立なら**並列**、A の結論が B の入力になるなら**逐次**で実行する。

## Step 5: クロスレビューで統合する
各サブエージェントのレポートが揃ったら、@chief として突き合わせる。意見が割れた論点だけ、
**同じサブエージェントに続きを送って**（SendMessage）他者の結論と根拠を見せ、反論・修正を求めてもよい
（第2ラウンド。見せるのは他の専門家の結論であって @chief の裁定ではない）：
```
### ✅ 全員が一致した点
### ⚠️ 意見が割れた点（論点 / 各専門家の立場 / 違いの背景）
### 🔴 矛盾・相反する推奨（内容 / A案根拠 / B案根拠 / @chiefの裁定）
```
**矛盾の解消順**：①根拠の強度（データ・規則・前例）②`memory/user-profile.md` の優先価値観
③過去の類似 `decisions.md` ④それでも割れたら矛盾を明示してユーザーに委ねる。
**多数決では決めない。根拠の強度で決める。**

## Step 6: 最終回答（@chief の出力フォーマット）

専門家名を出すときは、そのエージェント定義（`.claude/agents/{handle}.md`）の frontmatter `icon:` が絵文字なら
名前の前に添える（例：🧮 @accountant）。アイコン名（calculator 等）の場合は付けない（ボード専用）。
```
## {タスクのタイトル}
{1〜3文の結論・推奨}

### 詳細
{合意点／主要な考慮事項を観点別に}

### リスク
| リスク | 確率 | 影響 | 対策 |

### 不確かな点（情報次第で推奨が変わる）
- {情報X が判明すれば推奨が変わりうる}

---
**専門家の見解** ── {関与した@handle}
> {各専門家コメントを1行ずつ}

**次のアクション**: {具体的な1つ}
```
外部への実行（チケット作成・送信等）が次アクションなら、`memory/delegation.md` を確認し、
許可がなければ「▶ 実行してよいですか？」で締める。

## Step 7: 学習を記録する
- 統合で導いた推奨を `python tools/mem.py decision add --project {slug} --title … --prediction … --verify-date … --status proposed`
  で **提案（未承認）** として記録する。ユーザーが採用したら `decision set-status {slug} "{title}" decided`
  （/review-decisions が検証するのは決定だけ。ユーザーの承認前に「決定」と書かない）
- 専門家間の対立パターン・どの観点が効いたかを `memory/insights.md` に記録
